# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GraceBooks is a finance/membership management system for Tagaytay United Methodist Church, built as a static Firebase Hosting site — no build step, no bundler, no npm dependencies. Each page in `public/` is a self-contained HTML file with inline `<style>` and `<script>` blocks. Firebase is loaded via CDN `<script>` tags using the **compat** SDK (v10.7.1), not the modular SDK.

## Commands

There is no build/lint/test tooling in this repo (no `package.json`). Common operations are via the Firebase CLI:

```
firebase deploy --only hosting --project gracebooks-7eebc
firebase deploy --only firestore:rules --project gracebooks-7eebc
firebase deploy --only storage --project gracebooks-7eebc
```

On Windows, deploys are typically run as `cmd /c firebase deploy --only hosting --project gracebooks-7eebc` (per `PHASE-PLAN.md`). The default project is `gracebooks-7eebc` (set in `.firebaserc`).

To preview locally, serve `public/` with any static file server (e.g. `firebase emulators:start --only hosting` or `npx serve public`) — pages assume relative links to siblings in the same directory.

## Architecture

### Page structure
Every feature lives in its own top-level HTML file in `public/` (e.g. `tithe-entry.html`, `expenses.html`, `reports.html`, `print-report.html`). There are no shared JS modules or templates beyond `auth.js` — each page duplicates its own markup, styles, and Firestore logic inline. When fixing a bug or adding a feature, expect to edit a single large HTML file (many are 1,000–2,000+ lines).

`index.html` is the login screen and main dashboard. After login it renders a role-specific menu (the `menus` object keyed by role name) linking to the pages that role is allowed to use. `dashboard.html` is a dead redirect stub back to `index.html`.

### Auth flow (`auth.js`)
Loaded by every authenticated page after the Firebase compat scripts. Provides:
- `requireGraceBooksAuth()` — call once per page; redirects to `index.html` if not signed in, otherwise resolves `window.graceBooksAuthReady` with the user's profile and fires a `gracebooks-auth-ready` DOM event.
- `getGraceBooksProfile(user)` — fetches/caches the `userProfiles/{uid}` Firestore doc (role + name) into `sessionStorage` under `graceBooksUser`.
- `graceBooksLogout()` — signs out and clears `sessionStorage`.

Login uses Firebase Auth email/password with synthetic emails (`username@gracebooks.local` unless an `@` is already typed). Roles are **not** stored in Firebase Auth custom claims — they live in the `userProfiles` Firestore collection and are looked up by UID. Client-side writes to `userProfiles` are denied by Firestore rules; new users/roles must be provisioned via the Firebase Console (see `AUTH-MIGRATION.md`).

### Roles
Defined roles (see `AUTH-MIGRATION.md` and `firestore.rules`): `Treasurer`, `Pastor`, `Finance Chair`, `Chairperson`, `Deaconess`, `Admin Assistant`, `Auditor`, `District`, `Money Counter`, `Membership Secretary`, `Finance Committee`. Treasurer is the primary editor for nearly all financial collections; most other roles are read-only or scoped to a single page (e.g. Membership Secretary only sees attendance/member tools, Money Counter only sees income entry). `Finance Committee` is a read-only role scoped to Reports, Print Report, and Budget vs Actual, plus a restricted view of Financial Overview (see below) — distinct from `Finance Chair`, which is part of the report-workflow approval chain.

`Money Counter` is **create-only**, and that asymmetry is easy to trip over: per `firestore.rules` it may `create` on `income` and on `members` but has no `update` on either, and no `read` on `income` at all. So `tithe-entry.html` must never write a `members` document that already exists (a `setDoc` onto an existing id is an *update* and fails for that role - hence `createNewMemberDoc()`'s transactional "first genuinely free id" allocation), and must never navigate a Money Counter to `income-log.html` or any other page that reads `income`.

Any signed-in user can change their own password from the dashboard topbar (`index.html`, the key icon) via Firebase Auth reauthentication + `updatePassword` — this does not touch `userProfiles` (which stays server-provisioned only) and works the same for every role.

`financial-overview.html` is restricted to `Treasurer`, `Pastor`, `Auditor`, and `Finance Committee` (any other role is redirected to `index.html`). Only `Treasurer` sees transaction-level detail and the add/transfer/withdraw/cash-control mutation controls (elements marked with the `treasurer-only-financial` class, toggled in `applyFinancialRoleAccess()`); `Pastor`/`Auditor`/`Finance Committee` see account balances and the Cash Level Monitoring (Green/Yellow/Red/Black) card with its explanations, but not the transaction list, account-detail transaction history, or Statement generator.

### Report Archive (saved/versioned reports)
`report-archive.html` lists dated, downloadable snapshots saved from `financial-overview.html`, `reports.html`, and `budget-vs-actual.html` via each page's Treasurer-only "Generate & Save Version" button. Each version is a self-contained HTML file (open it and use the browser's own Print > Save as PDF to download) uploaded to Cloud Storage at `report-archive/{docId}/snapshot.html`, with metadata (title, period, who generated it, when) in the `reportArchive` Firestore collection. Only `Treasurer` can create/delete versions; `Treasurer`, `Auditor`, `Pastor`, `Chairperson`, and `Finance Committee` can read the archive and view/download versions - `Chairperson` does not have live access to any of the three source pages, only to their saved versions here. The Financial Overview snapshot always excludes individual transaction detail, matching that page's own restriction for non-Treasurer viewers. Each save also writes a `report_version_saved` (or `_deleted`) entry to `auditLogs`.

### Membership roll (`members.html`)
`members.html` is the **official church membership roll**, stored in `membershipRoll` — not the `members` collection, which despite its name is the tither roster behind `tithers.html`/`member-report.html`. Readable by `Treasurer`/`Membership Secretary` (plus `Deaconess`/`Pastor`/`Chairperson`, who only reach it through `membership-attendance.html`'s reports); only `Treasurer`/`Membership Secretary` can write.

A member document carries `memberId`, `lastName`, `firstName`, `middleInitial`, `layOrg`, `membershipType`, `ageLevel`, `gender`, `birthday`, `remarks`, `status`, `misImported` (+ `misImportedAt`/`misImportedBy`). `middleInitial` is stored as a single upper-case letter (`normalizeMiddleInitial()` reduces a full middle name to its initial); `birthday` is ISO `YYYY-MM-DD` as written by the date input, and `formatBirthday()` renders it `D-MMM-YYYY` while passing any older free-text value through untouched. Names render through `memberFullName()` as `Last, First M.` — duplicated in `membership-attendance.html` per the no-shared-components convention, so keep the two in step.

Membership types are `Professing Member`, `Baptized Member`, `Associate`, `Affiliate`, `No Membership Class`, `Pastor`, `Deaconess`; statuses are `Active`, `Inactive`, `Overseas`. Nothing outside those lists is rejected: the **Membership Class** stat tiles and the roll export both build their category/age-level/status tables from the values **actually present** on the roll (`orderedValues()` + `matchesValue()`), so a class added later or an older spelling carried in from a spreadsheet still reports rather than vanishing from a total. Adding a type means adding it to `MEMBERSHIP_TYPES` and a `.badge-*` colour — nothing else.

`No Membership Class` is a real, deliberately-chosen class and must never double as the label for "nobody recorded one": a member the secretary classified and a member nobody got to are different facts. A blank field buckets under the shared `UNRECORDED` (`'(not recorded)'`) constant instead, which no real option equals. `matchesValue()` also tolerates a collision (a fallback bucket matches both blank and its own spelling) and `orderedValues()` will not emit the same bucket twice, so a future label clash degrades to a merged bucket rather than to silently uncounted members.

`misImported` marks a member whose record has already been keyed into the UMC **Ministry Information System**. It is flipped by a toggle switch straight from the table row (`toggleMisImported()`), saved immediately as a field-level `.update()` rather than a whole-document `.set()`, and reverted in the UI if the write fails — a row that looks ticked but was never written is exactly how a member gets missed. Each flip writes a `member_mis_flag_changed` audit entry and stamps `misImportedAt`/`misImportedBy`; editing an already-imported member through the modal preserves the original stamp. `isMisImported()` reads anything a spreadsheet might carry (`yes`/`y`/`true`/`1`/`imported`) as imported and everything else — including an absent field on an older document — as not yet imported, which is the safe default. The table has a MIS filter and a MIS sort, and the export's **Summary** sheet carries an imported/remaining/total line; the roll sheet itself stays at the office's six columns.

`exportMembershipRoll()` writes a genuine two-sheet `.xlsx` (Summary + Membership Roll) reproducing the church's own audited roll workbook. Because there is no bundler and no npm, it builds the OOXML parts as strings and packs them into a store-only ZIP inline in the page — no spreadsheet library. If you touch it, keep the two summary tables on their existing different bases: **Age-Level counts the whole roll, Membership Category counts active members only**, which is what makes `TOTAL ACTIVE + Total Add = TOTAL MEMBERS` reconcile. Every export writes a `membership_roll_exported` audit entry.

CSV import matches columns by **header name** (`CSV_HEADER_FIELDS`), falling back to the original positional order when no header is recognised, and parses quoted fields — `remarks` routinely contains a comma. Multi-line quoted fields are not supported.

### Cash Vouchers
`cash-voucher.html` is the digital counterpart of the church's paper Cash Voucher form (UMC letterhead, Account/Date line, a Particulars/Amount table, Released by / Received by signature lines), storing each voucher in the `cashVouchers` collection. Restricted to `Treasurer` (full create/edit/delete, plus a signature/defaults card) and `Auditor` (read-only register and view/print); any other role is redirected to `index.html`, following `financial-overview.html`'s role-gate pattern. Voucher numbers (`CV-<YYYY>-<NNNN>`, resetting each calendar year) are allocated inside a `db.runTransaction()` against `settings/voucherSettings` so two vouchers saved at once can't collide — never a client-side `count + 1`. The Treasurer's "Released by" signature reuses the same `userSignatures/{uid}` doc and `signatures/{uid}/...` path as `report-workflow.html`, so one saved signature works on both pages; per explicit owner request, "always embed my signature as Released by" defaults to **on** whenever a signature exists - `autoEmbedEnabled()` treats only an explicit `false` (the Treasurer unticking the box) as off, since an absent/undefined setting means "never chosen" and must not read as off. That matters precisely because the signature is shared with `report-workflow.html`: a Treasurer who saved one there never ran this page's save flow, and an earlier `if (settings.autoEmbedTreasurerSignature && hasSig)` check silently produced unsigned vouchers for exactly that case. The voucher's two signature columns render the signer's **name** as the caption with the role ("Church Treasurer") as a smaller sub-caption beneath. `expenses.html` and `liquidation-reimbursements.html` each link into `cash-voucher.html?expenseId=`/`?liquidationId=` and get `voucherId`/`voucherNo` written back onto their own document once a voucher is created, so their ledgers can show a voucher badge without querying a second collection.

**Purpose (auditor request).** A voucher carries an optional free-text `purpose` (the rationale: what it was for, which event/ministry), printed as a "Purpose:" line under the Particulars table only when set, prefilled from the linked expense's/liquidation request's `notes`; saving without one asks for confirmation. It stays on the voucher - the Print Report lines are not lengthened.

### Data model (Firestore, see `firestore.rules`)
Key top-level collections: `userProfiles`, `userSignatures`, `income`, `expenses`, `members`, `attendance`, `churchObligations`, `reportReviews` (report workflow/approval state), `liquidationRequests`, `specialProjects` / `specialProjectEntries` / `specialProjectCosts`, `auditLogs`, `budgets`, `settings`, `reportArchive` (saved/versioned report snapshots, see below), `cashVouchers` (digital cash vouchers, see below), `countSheets` (photographed Sunday count sheets, see below). Access is gated per-collection by role via the `hasRole([...])` helper in rules; there is a catch-all deny at the bottom (`match /{document=**}`).

### Count Sheets
`countSheets` holds one doc per Sunday cash-counting session, tying together the physical paper count sheet's photo(s) with the `income` docs that session produced. A doc carries `date` (service date, `YYYY-MM-DD`), `createdAt`/`createdBy` (`{uid, name, role}`), `entryCount`/`totalAmount`/`cashTotal`/`nonCashTotal`, `denominations` (the same bill/coin breakdown `tithe-entry.html`'s Cash Denomination Check already collects, now persisted instead of only validated in the UI), `countedCashTotal` (the denominations' own total, in pesos - `Σ denomination.value × count`), `files` (`[{fileId, name, path, url, contentType, size}]`), and `notes`. Each `income` doc created alongside a sheet carries a matching `countSheetId`.

`countedCashTotal` exists specifically so `report-workflow.html`'s Income section has something independent to check the physical count against. Comparing the sheet's `totalAmount` to the date's income total is meaningless as a cash-count check - `totalAmount` is computed from the very same income docs the sheet is linked to, so it can only ever equal itself; it only drifts later if the Treasurer edits/deletes one of those entries, which the card surfaces separately as "Entries changed since count." The real check is `countedCashTotal` (what the denominations add up to) against that date's **recorded cash income** (`payment === 'Cash'`), which are two genuinely independent numbers - one written down at count time from what's physically in hand, the other summed from what got keyed in. The check only runs when a sheet has a nonzero `countedCashTotal` saved; otherwise the card shows "No denomination count saved" rather than a false match.

Saving the count sheet in `tithe-entry.html` is deliberately **best-effort**: it's wrapped in its own try/catch, separate from the income save loop, because a Storage/Firestore hiccup on the count sheet must never block the actual Sunday income (the weekly critical path) from being saved. On failure it asks the counter whether to save the income anyway; if so, every entry in that batch saves without a `countSheetId` (never a dangling id pointing at a `countSheets` doc that was never actually `setDoc`'d) and the session's `graceBooksCountSheetState` resets so the next batch starts clean, and a `count_sheet_save_failed` audit entry is written. If the counter says no instead, the whole batch stops and both the drafts and the count-sheet state (including any already-uploaded files) are left in place for a straightforward retry.

Firestore: read - `Treasurer`/`Auditor`/`Pastor`/`Finance Chair`/`Chairperson`/`Finance Committee`; create - `Treasurer`/`Money Counter`; update/delete - `Treasurer` only. **`Money Counter` is create-only here, exactly as on `income`** - it can save the sheet it just counted but never revise it afterward, and (like `income`) it has no read access at all. This matters mechanically in `tithe-entry.html`: the sheet's id is allocated client-side (`doc(collection(db,'countSheets')).id`) once per batch and persisted alongside the existing draft-record `sessionStorage` state, so a reload/retry mid-batch reuses the same id - a second `setDoc` on an existing doc is an *update*, which would fail for Money Counter exactly like the tither-roster `setDoc`-onto-existing-id trap `createNewMemberDoc()` already guards against above.

`tithe-entry.html`'s review/confirm step has an optional "Attach Count Sheet Photo(s)" input (camera-friendly, multiple files, image/PDF); `income-log.html` gives the Treasurer a small "Attach Count Sheet" button/modal to attach one after the fact to a past Sunday's entries that don't yet have one (it `update()`s those `income` docs with `countSheetId` - Treasurer has `update` on `income`). Both flows write a `count_sheet_created` audit entry.

**Scope: weekly vs monthly sheets.** A `countSheets` doc may carry `scope`. Docs with no `scope` (every existing one) are **weekly** (`'week'`) - one Sunday's counting session, exactly as above. `scope: 'month'` marks a **monthly tally sheet**: `month` (`YYYY-MM`), `date` (`YYYY-MM-01`), `createdAt`/`createdBy`, `files`, `notes`, optional `monthlyTotal` (the total the Treasurer types from the sheet, in pesos); it has NO `denominations`, `entryCount` or `totalAmount`, and is NOT linked to any `income` doc (weekly `countSheetId` links are untouched). One doc per month: the id is `monthly-YYYY-MM` when created by the app, and every attach flow first queries `where('month','==',m)` and appends to whatever month doc exists (arrayUnion) instead of creating a second. **Weekly logic must ignore month docs**: the `date` `YYYY-MM-01` can collide with a Sunday and a date-range query returns them, so every place that builds a Sunday's sheet list from a date query (`print-report.html`'s `ensureReviewSupportData()`/`reviewCountSheetMap`, the `s.date === date` lookups in the viewers, `income-log.html`'s per-date sheet list) drops `scope === 'month'` docs; month docs live in their own map (`supportingDocsMonthSheets` / `reviewMonthSheetMap`) so counted cash, "No count sheet" and "Entries changed since count" never see them.

**Adding files later.** The Treasurer can add photos/files to a sheet that already exists (a second photo, the back of the sheet, a receipt): uploads go to `count-sheets/{sheetId}/{uid}/{token}{ext}` (images/PDF, <= 5MB, same helpers as the new-sheet attach) and are appended with `update({files: FieldValue.arrayUnion(...)})` so a concurrent edit is not clobbered, then a `count_sheet_files_added` audit entry (`{sheetId, fileNames}`) is written. Entry points: `income-log.html`'s Attach Count Sheet modal (a "Save to" select offers the date's existing sheets next to "New count sheet"), an "Add photo/file" button beside "View Count Sheet" in `report-workflow.html`'s Supporting Documents Income rows and in `print-report.html` review-mode income panels (with more than one sheet for the date a prompt asks which; default is the first). Viewers already list every file in `files` (chooser for 2+). No rules change was needed: Treasurer already has `update` on `countSheets` and the storage path only checks the uploader's uid.

**Monthly tally sheet UI (Treasurer-only writes).** `income-log.html` has an "Attach Monthly Sheet" button/modal (month picker, multiple files, optional "Sheet total", notes; appends to an existing month doc, else creates one; audit `monthly_count_sheet_created` or `count_sheet_files_added`). `report-workflow.html`'s Supporting Documents Income section shows a header line above the per-Sunday summary - monthly reports: "Monthly tally sheet: View (n files) [Add files]" or a red "No monthly sheet" + "Attach monthly sheet" (Treasurer); annual reports list each month that has income or a sheet compactly. When `monthlyTotal` is set it is compared with that month's recorded income on the section's own basis (period income, `type === 'transfer'` excluded) and a red badge shows "Sheet total X != recorded Y" on a mismatch. `print-report.html` review mode (`?review=1` only) shows the same line as a review-only row (`review-panel-row review-only`, `#review-monthly-sheet-box`) at the top of Receipts / Income - hidden in print, skipped by the Excel export, never emitted on the normal page (its recorded total uses `incomeData`, which also drops the duplicate legacy cash advance returns). Month sheets are read one time per period with a `month` `==` / range query (a single-field query, no composite index). Same gating as the rest of the card: Treasurer always, Auditor only after submit (read-only), nobody else. Attaching from the report pages prompts for the optional sheet total; income-log has a field for it.

**Replacing / removing a sheet's files, and editing a monthly total (Treasurer only).** For an upload made by mistake, every place that lists or views a sheet's files gives the Treasurer **Replace** and **Remove** per file (in the file chooser; with exactly one file also inline beside "View"), for weekly and monthly sheets alike: `income-log.html` (a Treasurer-only "Manage Count Sheets" modal - pick a Sunday and/or a month; View/Replace/Remove/Add per file, plus Edit total/notes on a month), `report-workflow.html`'s Supporting Documents Income rows and monthly line, and `print-report.html` review-mode income panels and monthly line (review-only UI: `review-panel-row`s, hidden in print, skipped by the Excel export, never emitted on the normal page). Auditor, Money Counter and every other role see none of it, and every handler re-checks the role. **Replace** validates the new file (image/PDF, <= 5MB), uploads it to a NEW path `count-sheets/{sheetId}/{uid}/{token}{ext}`, then in a `db.runTransaction` reads the doc and swaps the entry with the matching `fileId` in place (same position) - never arrayRemove/arrayUnion on objects, which need exact equality - and only then deletes the OLD storage object best effort (a failed delete is `console.warn`ed and recorded in the audit entry; the doc is already correct). An upload failure changes nothing; a transaction failure deletes the new orphan (best effort) and leaves the doc as it was. Audit `count_sheet_file_replaced` (before/after file metadata, position, optional reason from a prompt, `oldStorageDeleted`/`oldStorageDeleteError`). **Remove** is confirm() -> transaction filtering `files` -> best-effort storage delete -> audit `count_sheet_file_removed`. A storage object is only ever deleted when its path is the `path` of an entry read from THAT sheet's own `files` inside the transaction AND starts with `count-sheets/{sheetId}/` (`csOwnPath()`), so a wrong `fileId` or a tampered path can never delete another sheet's file. **The `countSheets` doc is never deleted and no income entry is ever unlinked**: removing the last file leaves a sheet with no photo (weekly denominations and income links intact) - the weekly cell reads "Count sheet (no photo) · Add photo", a monthly sheet reads "No monthly sheet file" plus the attach button (which appends to the existing month doc). A monthly sheet's `monthlyTotal` and `notes` can be edited or cleared (blank total = `FieldValue.delete()`) from the same places via a transaction, audit `monthly_count_sheet_updated`; the mismatch badge is re-evaluated against the recorded income on refresh. Buttons carry ids in `data-cs-*` attributes handled by one delegated click listener (never inside inline JS strings), and the shared `cs*` helper block is duplicated per page like everything else here. No rules change: Firestore `countSheets` update and Storage `count-sheets/...` delete are already Treasurer-only.

Storage: `count-sheets/{sheetId}/{uid}/{fileName}` - read: any signed-in user; create/update: the uploader's own uid (verified from the path segment, not a `firestore.get()` - see the `liquidation-receipts/...` comment below) plus `validReceiptFile()` (images/PDF, ≤5MB); delete: `Treasurer` only. File names are generated tokens with a safe extension, never the original filename.

`expenses.receiptAnnotations` and `liquidationRequests.liquidationItems[].annotations` hold receipt-highlight boxes drawn with `public/receipt-annotator.js` (see below) - each an array of `{id, x, y, w, h, label, color, createdAt}` objects, with `x`/`y`/`w`/`h` as `0..1` fractions of the receipt image's width/height (never pixels), so the highlight overlay stays correctly positioned at any render size or device.

Highlights can be **locked** once finalized, so finished evidence can be reviewed without a stray drag altering it: `expenses.receiptAnnotationsLocked` (boolean, per expense) and `liquidationRequests.liquidationItems[].annotationsLocked` (boolean, per liquidation item - an item's highlights lock as a set across whichever receipts cover it). A locked set opens read-only even for a user with edit rights; they must click "Unlock to Edit" first, which persists the unlock immediately. The annotator takes `locked` as an option and reports it back as the second argument of `onSave(annotations, locked)`, so the highlights and their locked state are always written together and can never drift apart.

Rules currently include a `testingAccessOpen()` time-bomb (`request.time < timestamp.date(2027, 1, 1)`) that gates `signedIn()` — after that date all client access fails closed. The same expiry date is mirrored client-side in `index.html` (`TESTING_END_DATE`) to show a pre-expiry warning and block login.

### Council Dashboard (`council-dashboard.html`)
Ten-section projector/print/phone dashboard for the Church Council (spec: `COUNCIL-DASHBOARD-PLAN.md`). Roles: `Treasurer`, `Pastor`, `Auditor`, `Finance Chair`, `Chairperson`, `Finance Committee` (others redirect to `index.html`); the Stewardship & controls section (9) is Treasurer + Auditor only, and the closing "The bottom line" summary (10, last for every role; 9th for roles without section 9) is shown to all. A section whose collection the role cannot read (membership roll for Auditor/Finance Chair/Finance Committee) renders a muted "Not available for your role" tile - `membershipRoll` and `liquidationRequests` are only queried for roles `firestore.rules` lets read them, so no permission errors occur. No rules change.

**Pipeline.** `loadRaw()` does one-time reads of whole collections (income, expenses, obligations, projects, attendance, countSheets, settings...), then `computeKpis(raw, period, now)` builds one `kpi` object after `applyBasis(raw)` rebuilds module-level `incomeData`/`allIncomeData`/`expenseData`/`allExpenseData` named exactly as in `print-report.html`; every `render*`/`autoTalkingPoints`/snapshot reads only `kpi`. **Basis helpers are verbatim copies** (each commented "copied from X - keep in step"): `print-report.html` account resolution, `isGeneralFundAccount` (Building Fund always restricted), `isBuildingFundEntry`, `isDuplicateCashAdvanceReturn`, `getAccountBalancesThrough`, `outstandingWithholdingsThrough`, `buildingFundHeldInGfThrough`, the budget month helpers and main/sub classification; `financial-overview.html`'s `getCashLevel`; `budget-vs-actual.html`'s `trendBudgetedForMonth`/`trendCashLevel`/live available-operating-cash and projection. Receipts/Disbursements/Beginning/Ending Balance reconcile to the Print Report to the centavo (verified month by month, a contiguous run, and a non-contiguous selection against a stubbed Firestore).

**Period = year + any set of months.** Year picker, 12 toggle chips, presets (This/Last month, Q1-Q4, YTD, Full year, Clear). Totals/giving sum over the selected months (attendance is averaged; participation = unique tithers / average SUNDAY attendance (per-Sunday basis, see "Attendance basis" below)); budget = sum of each selected month's own budget; comparison = the same months last year. Beginning Balance is through the day before the first selected month, Ending through the end of the last; `computeStatement()` also computes the first..last span, and for a non-contiguous selection reports `inBetween` (the unselected months' net) so the waterfall shows an "Other months in between" bar plus a note and still ties out. A year's budget/report-review docs are fetched once and cached; chip clicks only recompute.

**Privacy.** Counts and percentages only - no giver names or per-person amounts anywhere (giver identity is used internally to count unique tithers and is never rendered or put in the snapshot). All user text goes through `escapeHtml`.

**Charts** are hand-rolled inline SVG drawn at the container's pixel width (re-rendered when the viewport WIDTH changes), colours from the validated reference palette (categorical slots 1-6, neutral "Other"; status colours reserved for cash levels, always with a label), `data-tip` tooltips and a "Table view" `<details>` per chart. The waterfall lifts its axis base (and says so) when changes are small next to the balances.

**Talking points** are generated per slide by `autoTalkingPoints(kpi)`; the Treasurer can edit them (one per line) and save to `settings/councilNotes-<YYYY-MM | YYYY-MM_MM... | YYYY-FY>` (audit `council_talking_points_saved`/`_reset`); an edited slide shows an "edited by the Treasurer" badge. **Presentation mode** (Slide show): one section per slide, arrows/Space/click/swipe, Esc exits. **Generate & Save Version** (Treasurer) writes a self-contained static HTML snapshot (dashboard CSS inlined, no scripts) to `report-archive/{docId}/snapshot.html` + `reportArchive` (`sourcePage: 'council-dashboard'`, listed by `report-archive.html`) and the usual `report_version_saved` audit entry.

**Attendance basis (average SUNDAY attendance).** Attendance is stored per Sunday by `membership-attendance.html` (`attendance/week-YYYY-MM-DD`: `serviceDate`, `attendance` = total headcount, `guests`, `presentMemberCount`, `entryType:'weekly'`); older `reports.html` entries are one monthly headcount (id `YYYY-MM`, no `serviceDate`); `attendance/_settings` is not a record (any id starting `_` is ignored). `buildAttendanceModel()`/`attendanceStats()` compute **average Sunday attendance = sum of Sunday headcounts / Sundays recorded** in the selected months; a legacy monthly doc is used ONLY for a month with no weekly docs, as that month's typical Sunday (one data point, marked "monthly figure (older record)" in the table view and `*` on the chart), never added on top of weekly docs. ### Budget vs Actual — Cash Budget tab (`budget-vs-actual.html`)
The tab's budget-based **Projected Cash Flow Timing** table is followed by a **Trend-Based Cash Projection — Cash Levels (Financial Overview basis)** section (shown to every role that can open the Cash Budget tab; no new writes, no rules change). ### Special Projects — proceeds postings (`special-projects.html`)
Project types: `Fund Raising` (always has a Proceeds tab), `Activity Contribution` (Proceeds tab only when `postProceedsToGeneralFund` is ticked), and `Construction Project` / `Equipment / Capital Project` / `Other Designated Fund`, which are **project-ledger only** (owner's rule for construction): their pledges/contributions/receipts live only in `specialProjectEntries` and never reach `income`. Net proceeds = gross receipts (`specialProjectEntries` `type: 'Receipt'`) − all expenses linked by `specialProjectId`; **net is the correct basis because event costs are paid out of the event's own collections** (owner-confirmed).

Proceeds post in **stages**, so an ongoing project can post now and post again later without duplicating income or rewriting an earlier month. The project carries `proceedsPostings: [{incomeId, amount, date, account, category, kind: 'posting'|'adjustment', netAtPost, grossAtPost, expensesAtPost, postedAt, postedBy}]`; each entry is its own `income` doc (Occasional Offering, `cash-hand`/`cash-bank`, `specialProjectId`, `proceedsPostingIndex`). Each new posting is exactly **current net − total already posted** (integer centavos, `proceedsPostingSummary()`), committed in a `db.runTransaction` that re-reads the project and aborts ("Postings changed since you opened this") if the posted total moved. If late costs push net below what was posted, the page shows "Over-posted by ₱X" and offers **Record correction**, a NEGATIVE `kind: 'adjustment'` income doc dated when recorded; earlier postings are never edited. **Undo Last Posting** deletes only the most recent posting (warning when it is dated in an earlier month). Deleting a project with postings is refused. Entries added to a Closed proceeds project ask for confirmation, and closing with a gap says so. Back-compat: older projects with only `linkedIncomeId`/`linkedIncomeAmount` read as one posting (`getProceedsPostings()`), and every write keeps those legacy fields in sync (`linkedIncomeId` = first posting, `linkedIncomeAmount` = total posted) for other readers. `print-report.html`'s special project report lists each posting plus a Total Posted row. Audits: `special_project_income_posted` / `_adjusted` / `_unposted`.

### Shared JS beyond `auth.js`
`public/receipt-annotator.js` is the one other shared script in this repo (`window.GraceBooksAnnotator`) — a framework-free canvas/DOM component for drawing and viewing labelled highlight boxes on a receipt image, loaded by both `expenses.html` and `liquidation-reimbursements.html` so the drag-to-highlight/legend/touch code isn't triplicated. It takes no Firebase dependency of its own — the calling page owns persistence and passes annotations in/out as plain objects (see the data-model note above). **Viewer size and rotation (view-only).** The modal uses ~95vw x 96vh (desktop: receipt on the left filling the height, tools/legend in a 300px right column; phone: receipt first at 60vh, tools below). A view bar offers Rotate left/right (90 deg steps), zoom -/+ (scrolls when zoomed) and Fit. Zoom is never saved; rotation is remembered per image (see below); neither touches annotation data: `layout()` sizes the *unrotated* stage to the fit-to-area size, rotates the whole stage (image + highlight overlay together) with a CSS transform, and sizes a wrapper to the rotated bounding box so nothing overflows. Drawing while rotated works: `fractionFromPoint()` undoes the rotation about the stage centre, so stored `x/y/w/h` stay fractions of the unrotated image (tested at 90 deg). Editable viewers also get a Pan/Draw toggle so a zoomed receipt can be scrolled by touch (the stage's `touch-action: none` only applies in draw mode). The annotator is the only in-page receipt/count-sheet image viewer; the chooser modals (`receiptViewerModal`, `reviewReceiptViewerModal`) just list files and open it, and PDFs/`income-log.html` "View" links open in a new tab.

**Saved rotation.** `public/receipt-rotation.js` (`window.GraceBooksReceiptRotation`, loaded right after the annotator on the same four pages) stores one doc per image in `receiptRotations/{sha256(storage path)}` = `{path, rotation (0/90/180/270), updatedAt, updatedBy}`. The key is the Storage object path decoded from the download URL's `/o/...` segment, so a re-issued token still finds it. The annotator stays Firebase-free and only calls this provider if present: on open it applies the saved rotation (unless the user already rotated), and on rotate it saves after a 700ms debounce - **Treasurer only** (`canSave()`; rules enforce `hasRole(['Treasurer'])` and a valid angle), with a small note ("Rotation saved for everyone" / "Rotation not saved (view only)" for other roles, who can still rotate locally). Read: `notMembershipSecretary()`. Display setting only, so no audit entry; the image and highlights never change.

Keep this the only other exception to "each page duplicates its own markup/logic" unless a third page needs the exact same UI.

Per `PHASE-PLAN.md` Phase 4B, treat all upload fields as security boundaries: enforce allowlisted file types, size limits, role checks, and audit logs; avoid trusting original filenames or rendering uploaded files as executable HTML.

### Report workflow
`report-workflow.html` implements a multi-step approval chain backed by `reportReviews` docs: Treasurer submits → Auditor + Finance Chair approve → routed to all signatories (Chairperson, Finance Chair, Treasurer, Auditor, Pastor) for signature → `print-report.html` renders the final signed report. Signature images are stored per-user in `userSignatures`/`signatures/{uid}`, not embedded per-report.

`report-workflow.html`'s **Supporting Documents** card (Treasurer/Auditor only; monthly/annual only - Special Projects has its own review page) one-time-fetches the period's `expenses` (a `date` range query, plus a second `isPayrollGenerated == true` query filtered client-side by `payrollMonth`, deduped by id) and splits them into an **Income** section (see below), an **Expenses** table (Date/Category/Payee/Amount/Receipt/Cash Voucher, with red "No receipt"/"No voucher" badges) and a **Salaries / Payroll** table (grouped per staff role per month, Admin + Admin Assistant merged as in `payslips.html`, linking out to `payslips.html?period=monthly&month=YYYY-MM&role=<Role>`). The receipt button reuses `expenses.html`'s `openReceiptViewer()` pattern (PDF → new tab, image → `GraceBooksAnnotator.open({..., editable:false})`), and the voucher link opens `cash-voucher.html?view=<voucherId>` - a read-only deep link (any allowed role, not just Treasurer) that the register's existing "View / Print" modal serves once the voucher is loaded or fetched by id. **Gating**: Treasurer always sees the card's links (to catch gaps before submitting); the Auditor only sees them once the report's `reportReviews` status has moved past `draft` (i.e. the Treasurer has submitted) - while in draft, or with no workflow doc yet, the Auditor sees a muted "Receipt links appear once the Treasurer submits this report." note instead. Every other role never gets the card at all.

**Liquidation-sourced receipts/vouchers.** An expense created from `liquidation-reimbursements.html` (`linkedLiquidationRequestId` set) usually has no `receiptUrl`/`voucherId` of its own - the receipts and cash voucher live on the `liquidationRequests` doc instead (see that page's section above). The card fetches those requests one time too (deduped, batched with `Promise.all` - both Treasurer and Auditor can read `liquidationRequests`) and `resolveExpenseReceipts()` works out what to show: the expense's own receipt if any; then, for an item the reconcile flow classified, every receipt in that item's `receiptIds` (matched back to `liquidationItems[]` conservatively by sub/amount/date - an ambiguous or missing match falls back to the request's whole receipt pool, labelled "Receipts on liquidation request", rather than guessing); then, for a reimbursement, the request's `supportingReceipts`/`receiptUrl`. More than one candidate renders as a small chooser ("View Receipts (n)") inside the receipt viewer modal; each opens the normal way (annotator for images, using the matched item's own annotations/lock state when resolved from one, or a new tab for PDFs). The voucher cell falls back from the expense's own `voucherId` to the linked request's `voucherId`/`voucherNo`. A cash advance that's been released but not yet liquidated (placeholder category, request status `Released`/`Liquidation Submitted`) reads amber **"Awaiting liquidation"** rather than a red "No receipt", and every linked row gets a small "🔗 Liquidation" link to `liquidation-reimbursements.html` (a plain link - that page has no deep-link support for one request).

**Overspent cash advances.** When a liquidation's items total MORE than the released advance, `liquidation-reimbursements.html`'s reconcile modal shows an allocation helper (overspent-with-items case only; underspent/exact reconciles are byte-identical to before): each item gets **From advance ₱** and **Reimburse ₱** inputs beside its one category select (which applies to both parts). Auto-assign (on open, the "Auto-assign" button, or the "Earliest/Largest items first" toggle) walks the items in that order filling the advance to the centavo, splitting the item that crosses the boundary; editing one side sets the other to (item amount − value), clamped to 0..amount; **Confirm is enabled only when every item's parts sum to its amount, the advance column equals the released amount and the reimburse column equals the excess exactly** - all in integer centavos (`toCents()`, never float sums). **No double count:** reconcile creates expenses ONLY for the advance parts (`amount` = advance part, plus `liquidationItemIndex`, and `liquidationSplit: 'advance'` when the item is split); the excess rides on the auto-created Reimbursement doc as `reimbursementItems[] = {index, date, description, amount (reimburse part), category, receiptIds, annotations}` (`amount` stays the excess total; `presetCategory` = category of the largest part, back-compat display only), and the source request's `liquidationItems[]` gain `advancePortion`/`reimbursePortion`. Releasing that reimbursement (`releaseAutoReimbursement()`, no single-category select) creates ONE expense per reimbursement item (`liquidationSplit: 'reimburse'`, `sourceLiquidationRequestId`, `liquidationItemIndex`, first receipt carried from the SOURCE request's receipt pool), dated on the item's own receipt date (`date` = the reimbursement item's `date`, with `budgetYear`/`expenseMonth` derived from it - the release date is only a fallback when the item has no usable ISO date; the `notes` still mention the item date), so a reimbursed part lands in the month it was actually spent, like the advance parts do and stores `linkedExpenseIds` (+ `linkedExpenseId` = first). Split expenses use deterministic ids (`liqrec-<reqId>-<i>`, `liqrel-<reqId>-<i>`, `liqtop-<reqId>`) so a retry after a mid-save failure overwrites rather than duplicates. **Legacy** auto-reimbursements (`sourceLiquidationRequestId` but no `reimbursementItems`, created by the old code) already had their excess expensed in full at reconciliation, so releasing one only marks it `Completed` (`settledAtReconciliation: true`) and creates NO expense; a legacy one already released with a `linkedExpenseId` that still exists shows a Treasurer-only "expensed twice - review and delete the duplicate" warning (never auto-deleted). Receipt resolution (`findMatchingLiquidationItem()` in `report-workflow.html` and `print-report.html`) prefers `expense.liquidationItemIndex` (guarded by a description match) over the sub/amount/date match - a split expense's partial amount defeats the latter - and for `liquidationSplit: 'reimburse'` resolves against the SOURCE request, which the one-time liquidation fetch now includes.

**Cash advance returns are silent.** Reconciling an UNDERSPENT cash advance deletes the release-time placeholder expense (full advance) and creates item expenses for the spent amount only - that alone restores the unspent money to the fund. It must NOT also create an income doc: the old `type:'transfer'`, `category:'Cash Advance Return'` income credited the fund a second time (advance 10,000, spent 8,000: records showed -6,000 instead of -8,000, because `financial-overview.html` adds income-transfers to the balance). The reconcile now keeps only `returnedAmount` on the request doc for display and writes a `liquidation_unspent_returned` audit entry. **Legacy** return docs (`category`/`budgetCategory`/`type` of 'Cash Advance Return') are handled two ways: `liquidation-reimbursements.html` shows the Treasurer a card listing them with a confirm()+audit-logged "Remove duplicate return entry" button (only when the linked request was reconciled with `liquidationItems`; a paper reconcile - no items, placeholder kept - is a legitimate return and shows "keep"; nothing is auto-deleted), and `print-report.html` excludes a duplicate from EVERY income-side pool (`isDuplicateCashAdvanceReturn()` applied where `allIncomeData` is built: incomeData, transfer netting, account balances, Restricted Fund Activity, review panels, Excel) using the same rule (linked request itemized - read from `liquidationRequests`, or inferred from categorized expenses linked to it for roles that cannot read that collection). Until removed, Financial Overview still counts them, so the Print Report shows a screen-only note with the difference.

**Income section**, above Expenses: the period's `income` (`date` range query, excluding `type === 'transfer'`; restricted-fund income is kept, matching the Expenses table's own choice not to filter by fund) grouped by date. Each row shows entry count/total/cash-vs-non-cash split and a "View Count Sheet" link or chooser (see Count Sheets above) for that date's `countSheets` doc(s), or a red "No count sheet" when none of that date's entries carry a `countSheetId`. When every entry for the date is linked and the sheet's saved `totalAmount` doesn't match the date's income total, a red mismatch badge shows both figures side by side. Summary line: "N Sundays · X missing count sheets".

### Print Report — Statement of Receipts and Disbursements basis
The monthly/annual statement in `print-report.html` (`generateReportHTML()`) is built on a **General Fund basis**, not a blended all-accounts basis: `fInc`/`fExp` (and so the Receipts/Disbursements sections, Total Cash Receipts/Disbursements, Ending Balance, and the Surplus/Deficit computation) only include entries whose account (`getIncomeAccountId`/`getExpenseAccountId`) is General Fund per `isGeneralFundAccount()` — itself a Treasurer-configurable per-account setting (Financial Overview > Beginning Balances), not a hardcoded list. Entries posted to a restricted account (e.g. Mission/Investment, unless the Treasurer opted them into the General Fund; the Building Fund is never opted in - see below) appear instead in a dedicated **Restricted Fund Activity** section (receipts in / disbursements out / net, per restricted account) right after Disbursements — they never silently vanish, which a legacy "skip Building Fund" filter on `incomeData` used to do.

**The Building Fund is ALWAYS restricted here** (owner's rule: it is a separate fund with different reporting, so it must never appear in the General Fund Receipts/Disbursements). Two mechanisms: (1) `isGeneralFundAccount('building')` is hardcoded `false`, whatever the Treasurer's `generalFundAccounts` setting says (every other account still follows the setting); (2) `isBuildingFundEntry(d)` classifies an income/expense ENTRY as Building Fund money when its explicit account is `building` OR its `budgetCategory`/`type`/`category` text contains "building fund" (the same test `budget-vs-actual.html`'s `isBuildingFund()` uses, applied to each field) - needed because a Building Fund entry can be posted to, or paid from, cash-hand/cash-bank, which the account alone would call General Fund. `isGeneralFundIncome()`/`isGeneralFundExpense()` (= not a Building Fund entry AND a General Fund account) decide `fInc`/`fExp`, the restricted rows and the YTD pools, so a Building Fund entry never reaches the GF Receipts/Disbursements, totals, Surplus/Deficit, Miscellaneous or the annual/YTD Budget columns (budget keys naming the Building Fund are also dropped from the GF budget structure, so their budget can't inflate Total Budget either). Transfers are not text-classified - they stay decided by their account alone, so a transfer into/out of `building` is a General Fund `Net Fund Transfers` line plus the Building Fund's `Transfers (Net)` line, as before. Building Fund money is reported ONLY under **Restricted Fund Activity -> Building Fund** (`getIncomeReportAccountId()`/`getExpenseReportAccountId()` bucket a Building Fund entry sitting in a General Fund account under `building`; one in another restricted account, e.g. an un-ticked Mission, stays under that account), and its `rst|building` review panel lists those entries (receipts, count sheets) like any other restricted account.

**Building Fund money held in General Fund accounts (reconciling line).** A Building Fund entry posted to a GF account (say a Building Fund offering recorded into cash-hand) moves that account's true cash balance but is not a GF receipt/disbursement, so the GF accounts would exceed the printed Ending Balance by exactly that cash - it is earmarked, not free GF cash. `buildingFundHeldInGfThrough(date)` = cumulative (Building Fund income on GF accounts - Building Fund expenses on GF accounts, at gross `d.amount` like the period math) and is handled exactly like the payroll withholdings: subtracted from BOTH `begBal` (day before the period) and the reconciliation comparison point (period end), so `begBal + netChange + netTransferGF === gfTrueEndBalance - withholdingsAtEnd - buildingHeldAtEnd` still holds algebraically and Ending Balance carries into the next period's Beginning Balance. It is shown as its own **"Building Fund money held in General Fund accounts (cumulative)"** line beside the payroll one whenever nonzero, and the green check then reads "(net of ... and Building Fund money held)". Verified with a June -> July -> annual Playwright harness (explicit `building` income, Building Fund income posted to cash-hand, a "Building Fund - Construction" expense paid from cash, a cash-hand -> building transfer, payroll withholding): Ending equalled the next Beginning to the centavo and the reconciliation was green in all three.

**Fund transfers** (`type: 'transfer'`, see `financial-overview.html`'s `transferFunds()`: paired `expenses`/`income` docs debiting the source account and crediting the destination) are excluded from `incomeData`/`expenseData` entirely — a transfer is cash movement, not real income/expense. Because of that, a transfer crossing between a General Fund account and a restricted one used to be invisible to this statement's own beginning/ending balance math, silently drifting the printed Ending Balance away from the true account balances every time one happened. `generateReportHTML()` now nets the period's transfer docs by General-Fund-ness into its own labelled **"Net Fund Transfers (into)/out of General Fund"** line. The mirror-image restricted-side effect of the same transfers is folded into each restricted account's own figures in the **Restricted Fund Activity** section too (a "Transfers (Net)" sub-line alongside Receipts In/Disbursements Out), so a restricted account's own Net there ties to that account's true balance movement for the period, not just its ordinary income/expense.

**The balance pools deliberately mirror `financial-overview.html`'s rules** so the Grand Total and each account balance tally with Financial Overview (proved with a harness that copies its listener + `combineAndRender()` logic verbatim and compares per-account balances). Income account: a typed fund (`Building Fund`/`Mission Fund`/`Investment Income`) OVERRIDES any explicit account, otherwise `targetAccount` (NOT `targetAccId`), else Cash in Bank for Bank Transfer, else Cash on Hand; expense account: `targetAccId`, else the payment mapping (Bank Transfer -> bank, Petty Cash -> petty cash), else Cash on Hand. An unknown account id is skipped by the balances (as in FO). Special-project income is skipped, all expenses (special-project costs, transfers, deduction-payments) count, payroll at net-pay cash impact, and an entry with no date counts as 2026-01-01 (applied where the docs are loaded, so statement and balances agree). `isBuildingFundEntry(d, isExpense)` uses that same resolved account, so a Building-Fund-typed income now always resolves to `building`; only text-classified entries ("building fund" in category/type text) posted to a General Fund account remain "held in General Fund accounts". The only intended difference from FO is the excluded legacy cash advance returns above. Not aligned on purpose: FO counts only entries dated up to today, whereas a statement reports through its period end.

**Beginning and Ending Balance must be on the same basis, or they won't carry over between periods.** `getAccountBalancesThrough()` recognizes payroll's cash impact at **net** pay (withheld tithe/SSS/other deductions leave cash later, via a separate `deduction-payment` record — see `getExpenseCashImpact()`), while this statement's own period math (`totalOut`, Total Disbursements) deliberately keeps payroll at **gross** pay so a reader sees the same figure that was budgeted/expensed. Naively computing Beginning Balance from the true (net-basis) account balance and Ending Balance from gross-basis period math would make one month's printed Ending Balance never equal the next month's printed Beginning Balance, by exactly whatever payroll withholding was still outstanding — an auditor would catch that immediately. The fix: both balances are put on **"cash net of payroll withholdings still held for remittance"** — `outstandingWithholdingsThrough(date)` computes the *cumulative* (all-time, not just this period) General-Fund payroll withheld minus remitted through a given date, and both `begBal` (through the day before the period) and the reconciliation's comparison point (through the period end) subtract it from the true account balance at that same date. Because the same adjustment applies identically at both ends, `begBal + netChange + netTransferGF` (the statement's own running total) is algebraically guaranteed to equal `gfTrueEndBalance - outstandingWithholdingsAtEnd`, so the **"General Fund accounts vs Ending Balance"** reconciliation check (green ✓ / red ✗, under a "General Fund Accounts" / "Restricted Funds" / "Grand Total, All Accounts" account listing that replaced the old flat "Financial Overview Accounts" section) should always read clean — a red ✗ means a genuine data problem, not an expected timing gap. The outstanding cumulative amount itself is still shown as its own labelled **"Payroll withholdings held for remittance (cumulative)"** line whenever nonzero, so a reader can see exactly how much of the General Fund's cash is earmarked rather than free. Verified with a two-month Playwright harness (June → July, a partial remittance spanning the boundary) and an annual → next-January check: Ending Balance and the next period's Beginning Balance matched to the centavo both times.

Report-line "levelling": a sub-category's own total sits in `col-main` (the same column as its main-category total), while a further detail (indent-3) row's amount sits in `col-sub` — the two never share a column, so a reader can't mistake a sub-category's detail breakdown for additional amounts stacked on top of its own total. A detail row is emitted only when the *budget's own* multi-level key structure produces one (`accountOrder.expense` / `catKeyToMain` / `catKeyToSub`); free-text `d.sub`/notes no longer fragment a budget line into near-duplicate spellings the way `sub = sub + ' - ' + notes` used to. An unbudgeted/Miscellaneous line groups under a single **"Miscellaneous (Unbudgeted)"** main category, with near-duplicate sub-labels (e.g. "Meralco" vs "MERALCO") merged case/whitespace-insensitively (`normalizeGroupKey()`) while still displaying whichever spelling was seen first. `exportToExcel()` reads the same rendered table (by row/cell CSS class) so the Excel export always agrees with the screen and print layouts.

**Miscellaneous (Unbudgeted) labels.** Generic words are never a label (`cleanMiscLabel()`: source of funds, occasional/special offering, "not in (the) budget", miscellaneous, misc, others, other, unbudgeted, n/a, none, general - case/punctuation-insensitive), so the useless "Source Of Funds" line can't happen. `pickMiscLabel()` takes the first candidate that survives: income tries the budget category text (only when it says something specific) -> `budgetDetails` -> `notes` -> the member/payer name (unless "General Collection") -> the income `type` as the very last resort; expense tries `sub` (particulars) -> `notes` -> `payee` -> the category text. `normalizeGroupKey()` still merges spelling variants. Each Miscellaneous sub-line shows `(N entries · months)` - annual "Mar, Jun, Sep", monthly "5, 19 Sep" (`miscDetailText()`) - plus the single entry's payee/member when it adds information; a Miscellaneous expense label is shown whole (never split at " - " into a detail row). **Annual only**, a compact "Unbudgeted items to consider for next year's budget" table (Item / Side / Entries / Months / Total, biggest first) sits just before Church Obligations; it is a nested table in one colspan cell like Church Obligations (`unbudgeted-wrapper-row`/`-header-row`/`-row`, with their own `exportToExcel()` branches). Budget columns for these lines stay "—" and no amount or total changes.

**Income detail labels (payer-less collections).** Fund-type and non-member income (Loose Offering, Sunday School, Investment Income, Special/Occasional offerings...) is saved by `tithe-entry.html` with member "General Collection", so the specific "what" lives only in `budgetDetails`/`notes` (or nowhere). One labeling rule, duplicated in `print-report.html` and `reports.html`: (1) a real payer name (not blank/"Anonymous"/"General Collection"/"Loose Offering" - `isRealPayerName()`); (2) else the specific detail, `budgetDetails` then `notes`, after `cleanIncomeDetail()` (`cleanMiscLabel()` plus "general collection", "loose offering", "offering", "collection", "sunday school", "tithes", "investment income" as non-details); (3) else a dated fallback "<Type/Sub> — 7 Sep". Presentation only - no amount or total is derived from a label. In `print-report.html` **monthly**, every income sub-line lists named members first (`sel-member-sort`, unchanged) and then payer-less entries via `buildGeneralIncomeRows()`: Loose Offering/Sunday School one row per date ("Sunday, 7 Sep" + detail if any), other lines one row per label (detail, else dated fallback; several entries under one label sum with "(n entries)"). These are ordinary `- ` detail rows (col-sub amount), so `exportToExcel()`'s existing member-row branch exports them. A Miscellaneous line already named after its detail does not repeat it as a row. **Annual** stays concise and never lists members: a sub-line made only of payer-less entries gets a muted "(N collections/entries · Jan-Dec)" note (`incomeMonthsText()` collapses runs), and non-Sunday lines with specific details also list up to 8 detail rows by total plus "Others (n entries)" (`buildAnnualGeneralRows()`). The Miscellaneous sub-label no longer falls back to the member name "General Collection" (it uses the income type). In `reports.html`, `getIncomeBase()` refines the bare type with its budget sub ("Source of Funds - Loose Offering"), `getIncomeGroupKey()` appends the detail only when one exists (tables and Members list; no per-date explosion), and the Weekly Collection table uses `getIncomeEntryLabel()` (detail, else type + date); the charts show no income labels. Monthly member lists keep anonymous tithes as a single "Anonymous" row (not the dated fallback). All labels are user text: always `escapeHtml`. `tithe-entry.html` only sets a Budget Details placeholder hint (e.g. "e.g., BDO time deposit interest") in `evaluateMemberSection()` - never required, save flow untouched.

**Pass-through headings (Print Report).** `print-report.html` reads `settings/passThroughItems` once (a failed read or an empty list = no tags, and the page renders byte-for-byte as before - verified with a two-context diff of `#export-table` against the previous version in normal and review modes). A tagged Miscellaneous income line moves, with the same amount, from Miscellaneous (Unbudgeted) to a main heading **"Pass-through Collections (for remittance)"** in Receipts (one sub-line per tagged item); a tagged expense line moves to **"Pass-through Remittances"** in Disbursements. They use the ordinary main/sub row markup (so `exportToExcel()`, print and review-mode clickable panels pick them up unchanged), show "—" for Budget/% Used, sort after Miscellaneous, and are left out of the annual "Unbudgeted items to consider" table. Matching is `side + '|' + normalizeGroupKey(label)` from the same `pickMiscLabel()` sources, applied only to entries that would otherwise land in Miscellaneous, so Total Cash Receipts, Total Disbursements, Surplus/Deficit, Ending Balance and the reconciliation never change. A muted `misc-note` row "Still to remit: ₱X" (collected - remitted, cumulative through the period end, General Fund) appears under the Pass-through Remittances heading (under Pass-through Collections when the period has no remittance line).

**Church Obligations** renders as a compact nested `<table class="obligation-table">` (Obligation / Due Date / Amount / Paid / Balance / Status, plus a totals row) inside the outer `fs-table`'s existing single-cell section layout, rather than a status/due-date/settlement string crammed into `col-desc`. `exportToExcel()` must treat its rows specially: the wrapping `<tr class="obligation-wrapper-row">` holds the *entire* nested table in one `<td colspan>`, so it's skipped explicitly (its `innerText` would otherwise read as one meaningless giant cell) — the nested table's own `obligation-header-row`/`obligation-row`/`obligation-totals-row` rows are still visited by the same `querySelectorAll('tr')` walk right after it (nested rows appear in document order) and are handled by their own branches. A genuine ₱0.00 in that table (e.g. an obligation with nothing paid yet) is parsed with a separate `parsePesoStrict()`, not the pre-existing `parsePeso()` — that one's `parseFloat(...) || null` fallback reads a real zero as blank, which would silently drop a ₱0.00 Paid cell.

**Budget / % Used columns.** `budgets/{year}` is loaded once per year (`ensureBudgetsForYear()`, cached in `budgetsCache`, reloaded whenever the selected year changes) and mapped onto the exact same grouping the actuals already use: `catKeyToMain`/`catKeyToSub` for expenses, and an income-side equivalent `incKeyToMain`/`incKeyToSub` built the same way as `incOrderMain`/`incOrderSub`. A main category's budget is the sum of its subs' budgets. On the **annual** statement, Budget is the full `budgets.{expense,income}[key]` amount; on the **monthly** statement the columns are explicitly labelled **YTD Budget**/**YTD % Used** — Budget is the sum of `expenseBudgetForMonth`/`incomeBudgetForMonth`/`getScheduleMonths` (copied verbatim from `budget-vs-actual.html`, since there are no shared JS modules here) for January through the selected month, and the Actual half is a **separate YTD-filtered actual**, not the period's own Amount figure: `buildIncGroups()`/`buildExpGroups()` wrap the exact same per-row classification logic used to build the display-side `incGroups`/`expGroups` so it can be re-run, unchanged, against a YTD-filtered pool (`ytdIncomePool`/`ytdExpensePool`) into a parallel `ytdIncGroups`/`ytdExpGroups` — the existing per-period Amount column and all of the balance-continuity math above are completely untouched by this. Miscellaneous (Unbudgeted) always shows Budget "—" (it has no budget line by definition). % Used is coloured red above 100% on the expense side, amber below 100% on the income side, plain otherwise; Total Cash Receipts/Total Disbursements get a Total Budget/% Used line too. A "Show budget columns" checkbox (`#chk-budget-cols`, default on) toggles `showBudgetCols`, which controls both the column count (`COLSPAN`, 3 or 5) and whether the two extra `<td>`s are emitted at all — turning it off reproduces the original 3-column layout exactly, not just hidden columns. `exportToExcel()` picks up the extra cells generically via `appendBudgetCols()`, reading `tds[3]`/`tds[4]` whenever present.

### Real-time vs one-time reads
Project convention (see `PHASE-PLAN.md` Standing Notes): prefer one-time Firestore fetches for new features to avoid continuous read costs. `financial-overview.html` is a deliberate exception that still uses real-time listeners — **do not change its listener behavior without explicit approval**, and avoid touching its logic/design when implementing unrelated enhancements.
