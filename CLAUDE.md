# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GraceBooks is a finance/membership management system for Tagaytay United Methodist Church, built as a static Firebase Hosting site — no build step, no bundler, no npm dependencies. Each page in `public/` is a self-contained HTML file with inline `<style>` and `<script>` blocks. Firebase is loaded via CDN `<script>` tags using the **compat** SDK (v10.7.1), not the modular SDK.

## Commands

There is no build/lint/test tooling in this repo (no `package.json`). Common operations are via the Firebase CLI:

```
firebase deploy --only hosting --project gracebooks-7eebc
firebase deploy --only firestore:rules --project gracebooks-7eebc
firebase deploy --only storage --project gracebooks-7eebc
```

On Windows, deploys are typically run as `cmd /c firebase deploy --only hosting --project gracebooks-7eebc` (per `PHASE-PLAN.md`). The default project is `gracebooks-7eebc` (set in `.firebaserc`).

To preview locally, serve `public/` with any static file server (e.g. `firebase emulators:start --only hosting` or `npx serve public`) — pages assume relative links to siblings in the same directory.

## Architecture

### Page structure
Every feature lives in its own top-level HTML file in `public/` (e.g. `tithe-entry.html`, `expenses.html`, `reports.html`, `print-report.html`). There are no shared JS modules or templates beyond `auth.js` — each page duplicates its own markup, styles, and Firestore logic inline. When fixing a bug or adding a feature, expect to edit a single large HTML file (many are 1,000–2,000+ lines).

`index.html` is the login screen and main dashboard. After login it renders a role-specific menu (the `menus` object keyed by role name) linking to the pages that role is allowed to use. `dashboard.html` is a dead redirect stub back to `index.html`.

### Auth flow (`auth.js`)
Loaded by every authenticated page after the Firebase compat scripts. Provides:
- `requireGraceBooksAuth()` — call once per page; redirects to `index.html` if not signed in, otherwise resolves `window.graceBooksAuthReady` with the user's profile and fires a `gracebooks-auth-ready` DOM event.
- `getGraceBooksProfile(user)` — fetches/caches the `userProfiles/{uid}` Firestore doc (role + name) into `sessionStorage` under `graceBooksUser`.
- `graceBooksLogout()` — signs out and clears `sessionStorage`.

Login uses Firebase Auth email/password with synthetic emails (`username@gracebooks.local` unless an `@` is already typed). Roles are **not** stored in Firebase Auth custom claims — they live in the `userProfiles` Firestore collection and are looked up by UID. Client-side writes to `userProfiles` are denied by Firestore rules; new users/roles must be provisioned via the Firebase Console (see `AUTH-MIGRATION.md`).

### Roles
Defined roles (see `AUTH-MIGRATION.md` and `firestore.rules`): `Treasurer`, `Pastor`, `Finance Chair`, `Chairperson`, `Deaconess`, `Admin Assistant`, `Auditor`, `District`, `Money Counter`, `Membership Secretary`, `Finance Committee`. Treasurer is the primary editor for nearly all financial collections; most other roles are read-only or scoped to a single page (e.g. Membership Secretary only sees attendance/member tools, Money Counter only sees income entry). `Finance Committee` is a read-only role scoped to Reports, Print Report, and Budget vs Actual, plus a restricted view of Financial Overview (see below) — distinct from `Finance Chair`, which is part of the report-workflow approval chain.

`Money Counter` is **create-only**, and that asymmetry is easy to trip over: per `firestore.rules` it may `create` on `income` and on `members` but has no `update` on either, and no `read` on `income` at all. So `tithe-entry.html` must never write a `members` document that already exists (a `setDoc` onto an existing id is an *update* and fails for that role - hence `createNewMemberDoc()`'s transactional "first genuinely free id" allocation), and must never navigate a Money Counter to `income-log.html` or any other page that reads `income`.

Any signed-in user can change their own password from the dashboard topbar (`index.html`, the key icon) via Firebase Auth reauthentication + `updatePassword` — this does not touch `userProfiles` (which stays server-provisioned only) and works the same for every role.

`financial-overview.html` is restricted to `Treasurer`, `Pastor`, `Auditor`, and `Finance Committee` (any other role is redirected to `index.html`). Only `Treasurer` sees transaction-level detail and the add/transfer/withdraw/cash-control mutation controls (elements marked with the `treasurer-only-financial` class, toggled in `applyFinancialRoleAccess()`); `Pastor`/`Auditor`/`Finance Committee` see account balances and the Cash Level Monitoring (Green/Yellow/Red/Black) card with its explanations, but not the transaction list, account-detail transaction history, or Statement generator.

### Report Archive (saved/versioned reports)
`report-archive.html` lists dated, downloadable snapshots saved from `financial-overview.html`, `reports.html`, and `budget-vs-actual.html` via each page's Treasurer-only "Generate & Save Version" button. Each version is a self-contained HTML file (open it and use the browser's own Print > Save as PDF to download) uploaded to Cloud Storage at `report-archive/{docId}/snapshot.html`, with metadata (title, period, who generated it, when) in the `reportArchive` Firestore collection. Only `Treasurer` can create/delete versions; `Treasurer`, `Auditor`, `Pastor`, `Chairperson`, and `Finance Committee` can read the archive and view/download versions - `Chairperson` does not have live access to any of the three source pages, only to their saved versions here. The Financial Overview snapshot always excludes individual transaction detail, matching that page's own restriction for non-Treasurer viewers. Each save also writes a `report_version_saved` (or `_deleted`) entry to `auditLogs`.

### Membership roll (`members.html`)
`members.html` is the **official church membership roll**, stored in `membershipRoll` — not the `members` collection, which despite its name is the tither roster behind `tithers.html`/`member-report.html`. Readable by `Treasurer`/`Membership Secretary` (plus `Deaconess`/`Pastor`/`Chairperson`, who only reach it through `membership-attendance.html`'s reports); only `Treasurer`/`Membership Secretary` can write.

A member document carries `memberId`, `lastName`, `firstName`, `middleInitial`, `layOrg`, `membershipType`, `ageLevel`, `gender`, `birthday`, `remarks`, `status`, `misImported` (+ `misImportedAt`/`misImportedBy`). `middleInitial` is stored as a single upper-case letter (`normalizeMiddleInitial()` reduces a full middle name to its initial); `birthday` is ISO `YYYY-MM-DD` as written by the date input, and `formatBirthday()` renders it `D-MMM-YYYY` while passing any older free-text value through untouched. Names render through `memberFullName()` as `Last, First M.` — duplicated in `membership-attendance.html` per the no-shared-components convention, so keep the two in step.

Membership types are `Professing Member`, `Baptized Member`, `Associate`, `Affiliate`, `No Membership Class`, `Pastor`, `Deaconess`; statuses are `Active`, `Inactive`, `Overseas`. Nothing outside those lists is rejected: the **Membership Class** stat tiles and the roll export both build their category/age-level/status tables from the values **actually present** on the roll (`orderedValues()` + `matchesValue()`), so a class added later or an older spelling carried in from a spreadsheet still reports rather than vanishing from a total. Adding a type means adding it to `MEMBERSHIP_TYPES` and a `.badge-*` colour — nothing else.

`No Membership Class` is a real, deliberately-chosen class and must never double as the label for "nobody recorded one": a member the secretary classified and a member nobody got to are different facts. A blank field buckets under the shared `UNRECORDED` (`'(not recorded)'`) constant instead, which no real option equals. `matchesValue()` also tolerates a collision (a fallback bucket matches both blank and its own spelling) and `orderedValues()` will not emit the same bucket twice, so a future label clash degrades to a merged bucket rather than to silently uncounted members.

`misImported` marks a member whose record has already been keyed into the UMC **Ministry Information System**. It is flipped by a toggle switch straight from the table row (`toggleMisImported()`), saved immediately as a field-level `.update()` rather than a whole-document `.set()`, and reverted in the UI if the write fails — a row that looks ticked but was never written is exactly how a member gets missed. Each flip writes a `member_mis_flag_changed` audit entry and stamps `misImportedAt`/`misImportedBy`; editing an already-imported member through the modal preserves the original stamp. `isMisImported()` reads anything a spreadsheet might carry (`yes`/`y`/`true`/`1`/`imported`) as imported and everything else — including an absent field on an older document — as not yet imported, which is the safe default. The table has a MIS filter and a MIS sort, and the export's **Summary** sheet carries an imported/remaining/total line; the roll sheet itself stays at the office's six columns.

`exportMembershipRoll()` writes a genuine two-sheet `.xlsx` (Summary + Membership Roll) reproducing the church's own audited roll workbook. Because there is no bundler and no npm, it builds the OOXML parts as strings and packs them into a store-only ZIP inline in the page — no spreadsheet library. If you touch it, keep the two summary tables on their existing different bases: **Age-Level counts the whole roll, Membership Category counts active members only**, which is what makes `TOTAL ACTIVE + Total Add = TOTAL MEMBERS` reconcile. Every export writes a `membership_roll_exported` audit entry.

CSV import matches columns by **header name** (`CSV_HEADER_FIELDS`), falling back to the original positional order when no header is recognised, and parses quoted fields — `remarks` routinely contains a comma. Multi-line quoted fields are not supported.

### Cash Vouchers
`cash-voucher.html` is the digital counterpart of the church's paper Cash Voucher form (UMC letterhead, Account/Date line, a Particulars/Amount table, Released by / Received by signature lines), storing each voucher in the `cashVouchers` collection. Restricted to `Treasurer` (full create/edit/delete, plus a signature/defaults card) and `Auditor` (read-only register and view/print); any other role is redirected to `index.html`, following `financial-overview.html`'s role-gate pattern. Voucher numbers (`CV-<YYYY>-<NNNN>`, resetting each calendar year) are allocated inside a `db.runTransaction()` against `settings/voucherSettings` so two vouchers saved at once can't collide — never a client-side `count + 1`. The Treasurer's "Released by" signature reuses the same `userSignatures/{uid}` doc and `signatures/{uid}/...` path as `report-workflow.html`, so one saved signature works on both pages; per explicit owner request, "always embed my signature as Released by" defaults to **on** whenever a signature exists - `autoEmbedEnabled()` treats only an explicit `false` (the Treasurer unticking the box) as off, since an absent/undefined setting means "never chosen" and must not read as off. That matters precisely because the signature is shared with `report-workflow.html`: a Treasurer who saved one there never ran this page's save flow, and an earlier `if (settings.autoEmbedTreasurerSignature && hasSig)` check silently produced unsigned vouchers for exactly that case. The voucher's two signature columns render the signer's **name** as the caption with the role ("Church Treasurer") as a smaller sub-caption beneath. `expenses.html` and `liquidation-reimbursements.html` each link into `cash-voucher.html?expenseId=`/`?liquidationId=` and get `voucherId`/`voucherNo` written back onto their own document once a voucher is created, so their ledgers can show a voucher badge without querying a second collection.

### Data model (Firestore, see `firestore.rules`)
Key top-level collections: `userProfiles`, `userSignatures`, `income`, `expenses`, `members`, `attendance`, `churchObligations`, `reportReviews` (report workflow/approval state), `liquidationRequests`, `specialProjects` / `specialProjectEntries` / `specialProjectCosts`, `auditLogs`, `budgets`, `settings`, `reportArchive` (saved/versioned report snapshots, see below), `cashVouchers` (digital cash vouchers, see below), `countSheets` (photographed Sunday count sheets, see below). Access is gated per-collection by role via the `hasRole([...])` helper in rules; there is a catch-all deny at the bottom (`match /{document=**}`).

### Count Sheets
`countSheets` holds one doc per Sunday cash-counting session, tying together the physical paper count sheet's photo(s) with the `income` docs that session produced. A doc carries `date` (service date, `YYYY-MM-DD`), `createdAt`/`createdBy` (`{uid, name, role}`), `entryCount`/`totalAmount`/`cashTotal`/`nonCashTotal`, `denominations` (the same bill/coin breakdown `tithe-entry.html`'s Cash Denomination Check already collects, now persisted instead of only validated in the UI), `countedCashTotal` (the denominations' own total, in pesos - `Σ denomination.value × count`), `files` (`[{fileId, name, path, url, contentType, size}]`), and `notes`. Each `income` doc created alongside a sheet carries a matching `countSheetId`.

`countedCashTotal` exists specifically so `report-workflow.html`'s Income section has something independent to check the physical count against. Comparing the sheet's `totalAmount` to the date's income total is meaningless as a cash-count check - `totalAmount` is computed from the very same income docs the sheet is linked to, so it can only ever equal itself; it only drifts later if the Treasurer edits/deletes one of those entries, which the card surfaces separately as "Entries changed since count." The real check is `countedCashTotal` (what the denominations add up to) against that date's **recorded cash income** (`payment === 'Cash'`), which are two genuinely independent numbers - one written down at count time from what's physically in hand, the other summed from what got keyed in. The check only runs when a sheet has a nonzero `countedCashTotal` saved; otherwise the card shows "No denomination count saved" rather than a false match.

Saving the count sheet in `tithe-entry.html` is deliberately **best-effort**: it's wrapped in its own try/catch, separate from the income save loop, because a Storage/Firestore hiccup on the count sheet must never block the actual Sunday income (the weekly critical path) from being saved. On failure it asks the counter whether to save the income anyway; if so, every entry in that batch saves without a `countSheetId` (never a dangling id pointing at a `countSheets` doc that was never actually `setDoc`'d) and the session's `graceBooksCountSheetState` resets so the next batch starts clean, and a `count_sheet_save_failed` audit entry is written. If the counter says no instead, the whole batch stops and both the drafts and the count-sheet state (including any already-uploaded files) are left in place for a straightforward retry.

Firestore: read - `Treasurer`/`Auditor`/`Pastor`/`Finance Chair`/`Chairperson`/`Finance Committee`; create - `Treasurer`/`Money Counter`; update/delete - `Treasurer` only. **`Money Counter` is create-only here, exactly as on `income`** - it can save the sheet it just counted but never revise it afterward, and (like `income`) it has no read access at all. This matters mechanically in `tithe-entry.html`: the sheet's id is allocated client-side (`doc(collection(db,'countSheets')).id`) once per batch and persisted alongside the existing draft-record `sessionStorage` state, so a reload/retry mid-batch reuses the same id - a second `setDoc` on an existing doc is an *update*, which would fail for Money Counter exactly like the tither-roster `setDoc`-onto-existing-id trap `createNewMemberDoc()` already guards against above.

`tithe-entry.html`'s review/confirm step has an optional "Attach Count Sheet Photo(s)" input (camera-friendly, multiple files, image/PDF); `income-log.html` gives the Treasurer a small "Attach Count Sheet" button/modal to attach one after the fact to a past Sunday's entries that don't yet have one (it `update()`s those `income` docs with `countSheetId` - Treasurer has `update` on `income`). Both flows write a `count_sheet_created` audit entry.

Storage: `count-sheets/{sheetId}/{uid}/{fileName}` - read: any signed-in user; create/update: the uploader's own uid (verified from the path segment, not a `firestore.get()` - see the `liquidation-receipts/...` comment below) plus `validReceiptFile()` (images/PDF, ≤5MB); delete: `Treasurer` only. File names are generated tokens with a safe extension, never the original filename.

`expenses.receiptAnnotations` and `liquidationRequests.liquidationItems[].annotations` hold receipt-highlight boxes drawn with `public/receipt-annotator.js` (see below) - each an array of `{id, x, y, w, h, label, color, createdAt}` objects, with `x`/`y`/`w`/`h` as `0..1` fractions of the receipt image's width/height (never pixels), so the highlight overlay stays correctly positioned at any render size or device.

Highlights can be **locked** once finalized, so finished evidence can be reviewed without a stray drag altering it: `expenses.receiptAnnotationsLocked` (boolean, per expense) and `liquidationRequests.liquidationItems[].annotationsLocked` (boolean, per liquidation item - an item's highlights lock as a set across whichever receipts cover it). A locked set opens read-only even for a user with edit rights; they must click "Unlock to Edit" first, which persists the unlock immediately. The annotator takes `locked` as an option and reports it back as the second argument of `onSave(annotations, locked)`, so the highlights and their locked state are always written together and can never drift apart.

Rules currently include a `testingAccessOpen()` time-bomb (`request.time < timestamp.date(2027, 1, 1)`) that gates `signedIn()` — after that date all client access fails closed. The same expiry date is mirrored client-side in `index.html` (`TESTING_END_DATE`) to show a pre-expiry warning and block login.

### Audit logging
Mutating flows (expense create/update/delete, receipt removal, payroll generation, etc.) write to the `auditLogs` collection via a local `writeAuditLog(action, docId, beforeData, afterData, summary)` helper duplicated per page (see `expenses.html`). Follow this pattern — capture before/after snapshots and a human-readable summary — when adding new mutating actions. Only `Treasurer`/`Auditor` can read `auditLogs`; any signed-in user can create entries.

### File uploads (Storage rules)
Upload surfaces, each with its own path prefix and constraints (`storage.rules`):
- `expense-receipts/{expenseId}/{fileName}` and `project-proofs/{entryId}/{fileName}` — images/PDF, ≤5MB.
- `signatures/{uid}/{fileName}` — images only, ≤2MB, owner-only write/delete.
- `voucher-signatures/{voucherId}/{fileName}` — images only, ≤2MB, Treasurer-only write/delete. Holds a cash voucher's "Received by" signature — distinct from `signatures/{uid}/...` above because the receiver (a vendor, a driver, staff) is usually not a system user with their own uid; their signature is captured on the Treasurer's device instead and is owned by the voucher, not by an account.

### Shared JS beyond `auth.js`
`public/receipt-annotator.js` is the one other shared script in this repo (`window.GraceBooksAnnotator`) — a framework-free canvas/DOM component for drawing and viewing labelled highlight boxes on a receipt image, loaded by both `expenses.html` and `liquidation-reimbursements.html` so the drag-to-highlight/legend/touch code isn't triplicated. It takes no Firebase dependency of its own — the calling page owns persistence and passes annotations in/out as plain objects (see the data-model note above). Keep this the only other exception to "each page duplicates its own markup/logic" unless a third page needs the exact same UI.

Per `PHASE-PLAN.md` Phase 4B, treat all upload fields as security boundaries: enforce allowlisted file types, size limits, role checks, and audit logs; avoid trusting original filenames or rendering uploaded files as executable HTML.

### Report workflow
`report-workflow.html` implements a multi-step approval chain backed by `reportReviews` docs: Treasurer submits → Auditor + Finance Chair approve → routed to all signatories (Chairperson, Finance Chair, Treasurer, Auditor, Pastor) for signature → `print-report.html` renders the final signed report. Signature images are stored per-user in `userSignatures`/`signatures/{uid}`, not embedded per-report.

`report-workflow.html`'s **Supporting Documents** card (Treasurer/Auditor only; monthly/annual only - Special Projects has its own review page) one-time-fetches the period's `expenses` (a `date` range query, plus a second `isPayrollGenerated == true` query filtered client-side by `payrollMonth`, deduped by id) and splits them into an **Income** section (see below), an **Expenses** table (Date/Category/Payee/Amount/Receipt/Cash Voucher, with red "No receipt"/"No voucher" badges) and a **Salaries / Payroll** table (grouped per staff role per month, Admin + Admin Assistant merged as in `payslips.html`, linking out to `payslips.html?period=monthly&month=YYYY-MM&role=<Role>`). The receipt button reuses `expenses.html`'s `openReceiptViewer()` pattern (PDF → new tab, image → `GraceBooksAnnotator.open({..., editable:false})`), and the voucher link opens `cash-voucher.html?view=<voucherId>` - a read-only deep link (any allowed role, not just Treasurer) that the register's existing "View / Print" modal serves once the voucher is loaded or fetched by id. **Gating**: Treasurer always sees the card's links (to catch gaps before submitting); the Auditor only sees them once the report's `reportReviews` status has moved past `draft` (i.e. the Treasurer has submitted) - while in draft, or with no workflow doc yet, the Auditor sees a muted "Receipt links appear once the Treasurer submits this report." note instead. Every other role never gets the card at all.

**Liquidation-sourced receipts/vouchers.** An expense created from `liquidation-reimbursements.html` (`linkedLiquidationRequestId` set) usually has no `receiptUrl`/`voucherId` of its own - the receipts and cash voucher live on the `liquidationRequests` doc instead (see that page's section above). The card fetches those requests one time too (deduped, batched with `Promise.all` - both Treasurer and Auditor can read `liquidationRequests`) and `resolveExpenseReceipts()` works out what to show: the expense's own receipt if any; then, for an item the reconcile flow classified, every receipt in that item's `receiptIds` (matched back to `liquidationItems[]` conservatively by sub/amount/date - an ambiguous or missing match falls back to the request's whole receipt pool, labelled "Receipts on liquidation request", rather than guessing); then, for a reimbursement, the request's `supportingReceipts`/`receiptUrl`. More than one candidate renders as a small chooser ("View Receipts (n)") inside the receipt viewer modal; each opens the normal way (annotator for images, using the matched item's own annotations/lock state when resolved from one, or a new tab for PDFs). The voucher cell falls back from the expense's own `voucherId` to the linked request's `voucherId`/`voucherNo`. A cash advance that's been released but not yet liquidated (placeholder category, request status `Released`/`Liquidation Submitted`) reads amber **"Awaiting liquidation"** rather than a red "No receipt", and every linked row gets a small "🔗 Liquidation" link to `liquidation-reimbursements.html` (a plain link - that page has no deep-link support for one request).

**Overspent cash advances.** When a liquidation's items total MORE than the released advance, `liquidation-reimbursements.html`'s reconcile modal shows an allocation helper (overspent-with-items case only; underspent/exact reconciles are byte-identical to before): each item gets **From advance ₱** and **Reimburse ₱** inputs beside its one category select (which applies to both parts). Auto-assign (on open, the "Auto-assign" button, or the "Earliest/Largest items first" toggle) walks the items in that order filling the advance to the centavo, splitting the item that crosses the boundary; editing one side sets the other to (item amount − value), clamped to 0..amount; **Confirm is enabled only when every item's parts sum to its amount, the advance column equals the released amount and the reimburse column equals the excess exactly** - all in integer centavos (`toCents()`, never float sums). **No double count:** reconcile creates expenses ONLY for the advance parts (`amount` = advance part, plus `liquidationItemIndex`, and `liquidationSplit: 'advance'` when the item is split); the excess rides on the auto-created Reimbursement doc as `reimbursementItems[] = {index, date, description, amount (reimburse part), category, receiptIds, annotations}` (`amount` stays the excess total; `presetCategory` = category of the largest part, back-compat display only), and the source request's `liquidationItems[]` gain `advancePortion`/`reimbursePortion`. Releasing that reimbursement (`releaseAutoReimbursement()`, no single-category select) creates ONE expense per reimbursement item (`liquidationSplit: 'reimburse'`, `sourceLiquidationRequestId`, `liquidationItemIndex`, first receipt carried from the SOURCE request's receipt pool) and stores `linkedExpenseIds` (+ `linkedExpenseId` = first). Split expenses use deterministic ids (`liqrec-<reqId>-<i>`, `liqrel-<reqId>-<i>`, `liqtop-<reqId>`) so a retry after a mid-save failure overwrites rather than duplicates. **Legacy** auto-reimbursements (`sourceLiquidationRequestId` but no `reimbursementItems`, created by the old code) already had their excess expensed in full at reconciliation, so releasing one only marks it `Completed` (`settledAtReconciliation: true`) and creates NO expense; a legacy one already released with a `linkedExpenseId` that still exists shows a Treasurer-only "expensed twice - review and delete the duplicate" warning (never auto-deleted). Receipt resolution (`findMatchingLiquidationItem()` in `report-workflow.html` and `print-report.html`) prefers `expense.liquidationItemIndex` (guarded by a description match) over the sub/amount/date match - a split expense's partial amount defeats the latter - and for `liquidationSplit: 'reimburse'` resolves against the SOURCE request, which the one-time liquidation fetch now includes.

**Income section**, above Expenses: the period's `income` (`date` range query, excluding `type === 'transfer'`; restricted-fund income is kept, matching the Expenses table's own choice not to filter by fund) grouped by date. Each row shows entry count/total/cash-vs-non-cash split and a "View Count Sheet" link or chooser (see Count Sheets above) for that date's `countSheets` doc(s), or a red "No count sheet" when none of that date's entries carry a `countSheetId`. When every entry for the date is linked and the sheet's saved `totalAmount` doesn't match the date's income total, a red mismatch badge shows both figures side by side. Summary line: "N Sundays · X missing count sheets".

The receipt/voucher/payslip links live in this Supporting Documents card, and (see "Report Preview / review mode" below) directly on the statement itself when opened from here - `print-report.html` opened normally (no `review=1`) never carries any review-links feature, matching the owner's explicit constraint that a plain/printed report stays clean.

**Report Preview / review mode.** A "Report Preview" card (Treasurer/Auditor only, monthly/annual only - hidden for Special Projects, which has no such review UI) embeds the real statement in an `<iframe src="print-report.html?type=...&year=...&month=...&review=1">`, built the same way `openPrintReport()` builds its URL, and reloads whenever the report type/period changes (`loadReportPreview()`, called from `loadWorkflow()`). An "Open full screen ↗" link opens the same URL in a new tab. The iframe is same-origin, so Firebase auth is already shared - no separate sign-in inside it.

`review=1` is read by `print-report.html` itself and only ever turns on review mode when ALL of: the param is present; the role (from `sessionStorage.role`, refreshed from `graceBooksAuthReady` as a cold-load fallback) is Treasurer, or Auditor with this period's `reportReviews` status past `draft` (reusing the page's existing `currentWorkflowId()`/`loadWorkflowSignaturesForCurrentPeriod()` read, which now also captures `status`); and the report type is monthly or annual. Every other combination renders exactly as the normal page always has - `generateReportHTML()` only ever emits the extra `data-rk`/`📎` markup and `review-line` class when `reviewMode` is true, so the non-review page's `#export-table` HTML is byte-for-byte unchanged (verified with a two-context Playwright diff against the pre-change page for the same fixture).

In review mode, a small banner explains the mode, and the Income and Disbursements/Miscellaneous sub-category lines (`buildIncGroups()`/`buildExpGroups()`, extended to also collect each line's contributing income/expense docs into `reviewIncLineEntries`/`reviewExpLineEntries` - purely additive, no amount math touched) become clickable, inserting an inline panel row (`review-panel-row`) built lazily on click (`toggleReviewPanel()`), not upfront - so an annual report with hundreds of entries never pre-builds panels it wasn't asked for. `liquidationRequests` and `countSheets` for the period are fetched once, only in review mode, only the first time a panel is opened (`ensureReviewSupportData()`), never on page load and never for the normal page.

An expense panel resolves receipts the same way as `resolveExpenseReceipts()` above (copied verbatim - no shared JS modules here), shows a voucher link/badge, a 🔗 Liquidation link, and (payroll rows) a "View Payslip" link; an income panel groups entries by date and shows each date's count sheet status/mismatch the same way `renderIncomeSection()` above does. Receipts/count-sheet photos open the same way (`GraceBooksAnnotator` for images, a new tab for PDFs, a chooser for several candidates) via the page's own `#reviewReceiptViewerModal`.

### Print Report — Statement of Receipts and Disbursements basis
The monthly/annual statement in `print-report.html` (`generateReportHTML()`) is built on a **General Fund basis**, not a blended all-accounts basis: `fInc`/`fExp` (and so the Receipts/Disbursements sections, Total Cash Receipts/Disbursements, Ending Balance, and the Surplus/Deficit computation) only include entries whose account (`getIncomeAccountId`/`getExpenseAccountId`) is General Fund per `isGeneralFundAccount()` — itself a Treasurer-configurable per-account setting (Financial Overview > Beginning Balances), not a hardcoded list. Entries posted to a restricted account (e.g. Mission/Building/Investment, unless the Treasurer opted them into the General Fund) appear instead in a dedicated **Restricted Fund Activity** section (receipts in / disbursements out / net, per restricted account) right after Disbursements — they never silently vanish, which a legacy "skip Building Fund" filter on `incomeData` used to do.

**Fund transfers** (`type: 'transfer'`, see `financial-overview.html`'s `transferFunds()`: paired `expenses`/`income` docs debiting the source account and crediting the destination) are excluded from `incomeData`/`expenseData` entirely — a transfer is cash movement, not real income/expense. Because of that, a transfer crossing between a General Fund account and a restricted one used to be invisible to this statement's own beginning/ending balance math, silently drifting the printed Ending Balance away from the true account balances every time one happened. `generateReportHTML()` now nets the period's transfer docs by General-Fund-ness into its own labelled **"Net Fund Transfers (into)/out of General Fund"** line. The mirror-image restricted-side effect of the same transfers is folded into each restricted account's own figures in the **Restricted Fund Activity** section too (a "Transfers (Net)" sub-line alongside Receipts In/Disbursements Out), so a restricted account's own Net there ties to that account's true balance movement for the period, not just its ordinary income/expense.

**Beginning and Ending Balance must be on the same basis, or they won't carry over between periods.** `getAccountBalancesThrough()` recognizes payroll's cash impact at **net** pay (withheld tithe/SSS/other deductions leave cash later, via a separate `deduction-payment` record — see `getExpenseCashImpact()`), while this statement's own period math (`totalOut`, Total Disbursements) deliberately keeps payroll at **gross** pay so a reader sees the same figure that was budgeted/expensed. Naively computing Beginning Balance from the true (net-basis) account balance and Ending Balance from gross-basis period math would make one month's printed Ending Balance never equal the next month's printed Beginning Balance, by exactly whatever payroll withholding was still outstanding — an auditor would catch that immediately. The fix: both balances are put on **"cash net of payroll withholdings still held for remittance"** — `outstandingWithholdingsThrough(date)` computes the *cumulative* (all-time, not just this period) General-Fund payroll withheld minus remitted through a given date, and both `begBal` (through the day before the period) and the reconciliation's comparison point (through the period end) subtract it from the true account balance at that same date. Because the same adjustment applies identically at both ends, `begBal + netChange + netTransferGF` (the statement's own running total) is algebraically guaranteed to equal `gfTrueEndBalance - outstandingWithholdingsAtEnd`, so the **"General Fund accounts vs Ending Balance"** reconciliation check (green ✓ / red ✗, under a "General Fund Accounts" / "Restricted Funds" / "Grand Total, All Accounts" account listing that replaced the old flat "Financial Overview Accounts" section) should always read clean — a red ✗ means a genuine data problem, not an expected timing gap. The outstanding cumulative amount itself is still shown as its own labelled **"Payroll withholdings held for remittance (cumulative)"** line whenever nonzero, so a reader can see exactly how much of the General Fund's cash is earmarked rather than free. Verified with a two-month Playwright harness (June → July, a partial remittance spanning the boundary) and an annual → next-January check: Ending Balance and the next period's Beginning Balance matched to the centavo both times.

Report-line "levelling": a sub-category's own total sits in `col-main` (the same column as its main-category total), while a further detail (indent-3) row's amount sits in `col-sub` — the two never share a column, so a reader can't mistake a sub-category's detail breakdown for additional amounts stacked on top of its own total. A detail row is emitted only when the *budget's own* multi-level key structure produces one (`accountOrder.expense` / `catKeyToMain` / `catKeyToSub`); free-text `d.sub`/notes no longer fragment a budget line into near-duplicate spellings the way `sub = sub + ' - ' + notes` used to. An unbudgeted/Miscellaneous line groups under a single **"Miscellaneous (Unbudgeted)"** main category, with near-duplicate sub-labels (e.g. "Meralco" vs "MERALCO") merged case/whitespace-insensitively (`normalizeGroupKey()`) while still displaying whichever spelling was seen first. `exportToExcel()` reads the same rendered table (by row/cell CSS class) so the Excel export always agrees with the screen and print layouts.

**Miscellaneous (Unbudgeted) label source order.** Both the income and expense unbudgeted-grouping code pick each item's display label from a fixed candidate order, most-structured field first, so the same entry always gets the same label rather than whatever free text happened to be typed that day: expense tries the budget category text (`d.category`, "not in budget" stripped) → `d.sub` → payee → notes; income tries the budget category text (`d.budgetCategory`/`d.category`) → the income type (`d.type`) → notes/details. Each Miscellaneous sub-line also shows its entry count (`.entry-count`, e.g. "Hardware Supplies (3 entries)"), and the Miscellaneous main row carries a one-line muted `.misc-note` ("Items not in the approved budget — consider adding a budget line.").

**Church Obligations** renders as a compact nested `<table class="obligation-table">` (Obligation / Due Date / Amount / Paid / Balance / Status, plus a totals row) inside the outer `fs-table`'s existing single-cell section layout, rather than a status/due-date/settlement string crammed into `col-desc`. `exportToExcel()` must treat its rows specially: the wrapping `<tr class="obligation-wrapper-row">` holds the *entire* nested table in one `<td colspan>`, so it's skipped explicitly (its `innerText` would otherwise read as one meaningless giant cell) — the nested table's own `obligation-header-row`/`obligation-row`/`obligation-totals-row` rows are still visited by the same `querySelectorAll('tr')` walk right after it (nested rows appear in document order) and are handled by their own branches. A genuine ₱0.00 in that table (e.g. an obligation with nothing paid yet) is parsed with a separate `parsePesoStrict()`, not the pre-existing `parsePeso()` — that one's `parseFloat(...) || null` fallback reads a real zero as blank, which would silently drop a ₱0.00 Paid cell.

**Budget / % Used columns.** `budgets/{year}` is loaded once per year (`ensureBudgetsForYear()`, cached in `budgetsCache`, reloaded whenever the selected year changes) and mapped onto the exact same grouping the actuals already use: `catKeyToMain`/`catKeyToSub` for expenses, and an income-side equivalent `incKeyToMain`/`incKeyToSub` built the same way as `incOrderMain`/`incOrderSub`. A main category's budget is the sum of its subs' budgets. On the **annual** statement, Budget is the full `budgets.{expense,income}[key]` amount; on the **monthly** statement the columns are explicitly labelled **YTD Budget**/**YTD % Used** — Budget is the sum of `expenseBudgetForMonth`/`incomeBudgetForMonth`/`getScheduleMonths` (copied verbatim from `budget-vs-actual.html`, since there are no shared JS modules here) for January through the selected month, and the Actual half is a **separate YTD-filtered actual**, not the period's own Amount figure: `buildIncGroups()`/`buildExpGroups()` wrap the exact same per-row classification logic used to build the display-side `incGroups`/`expGroups` so it can be re-run, unchanged, against a YTD-filtered pool (`ytdIncomePool`/`ytdExpensePool`) into a parallel `ytdIncGroups`/`ytdExpGroups` — the existing per-period Amount column and all of the balance-continuity math above are completely untouched by this. Miscellaneous (Unbudgeted) always shows Budget "—" (it has no budget line by definition). % Used is coloured red above 100% on the expense side, amber below 100% on the income side, plain otherwise; Total Cash Receipts/Total Disbursements get a Total Budget/% Used line too. A "Show budget columns" checkbox (`#chk-budget-cols`, default on) toggles `showBudgetCols`, which controls both the column count (`COLSPAN`, 3 or 5) and whether the two extra `<td>`s are emitted at all — turning it off reproduces the original 3-column layout exactly, not just hidden columns. `exportToExcel()` picks up the extra cells generically via `appendBudgetCols()`, reading `tds[3]`/`tds[4]` whenever present.

### Real-time vs one-time reads
Project convention (see `PHASE-PLAN.md` Standing Notes): prefer one-time Firestore fetches for new features to avoid continuous read costs. `financial-overview.html` is a deliberate exception that still uses real-time listeners — **do not change its listener behavior without explicit approval**, and avoid touching its logic/design when implementing unrelated enhancements.
